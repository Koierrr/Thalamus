# 记忆引擎遥测与写入失败调查（只读调查 + 施工方案）

> **状态：已实施**（2026-09-13 全部落地）。遥测已四层关闭并实测验证；写失败已可见（后台红字）；引擎恢复后降级记忆会自动补迁。外发边界按用户裁决执行（提炼留云端、向量留本机）。实现细节见《工程实施档案（减法轮 + 加法轮 E1–E4）》与 `docs/记忆系统设计.md` 第八节。

调查对象：wechat-companion/ 的记忆层（插件 Node 侧 + python/memory_service.py sidecar + mem0 2.0.20 依赖）。
纪律：本文件只描述改法与验证方式，不含任何实际改动；所有结论都附日志原文、代码行或被实际执行过的只读命令输出。

摘要（四条）：

1. PostHog 遥测的初始化者是 mem0 自己（不是 chroma、不是别家库）：mem0 2.0.20 的 mem0/memory/telemetry.py 在导入时建一个模块级客户端，在首次 capture_event 时再建一个 OSS 单例 —— 两个客户端用同一个 project key，这正是日志里那句 Multiple active PostHog clients 的来源。
2. 插件配置里写的 telemetry: False 对 mem0 2.0.20 完全无效：MemoryConfig 没有 telemetry 字段，pydantic 静默丢弃。唯一的开关是环境变量 MEM0_TELEMETRY，且它在 import 时读取。
3. 数据确实发出去了：mem-engine.log 里有 21 行 PostHog 上传失败记录，目标 host 为 us.i.posthog.com:443；~/.mem0/config.json 里留下了持久匿名 id 与公告评估记录。发出去的是匿名 id + 版本/系统元数据 + 操作名 + md5 过的 user_id，不含记忆正文。
4. 写入失败是双层静默：sidecar 的 _body() 把解码/解析失败吞成 {}，插件的 readBody() 同样吞成 {}；然后 soul.addMemory 写失败时只记一行日志就落本地 JSON 并返回成功样子。日志里能查到的真实错误只有两种（name 'cfg' is not defined、Invalid query: cannot be empty or whitespace-only.），其中空 query 有一条 100% 会复现的代码路径：所有主动消息（早安/晚安/分享/催）都拿空串去检索。

### 1.4 发出去的是什么（字段清单，含「不含正文」的确认）

capture_event 组装的属性（mem0/memory/telemetry.py）：

    properties = {
      "client_source": "python", "client_version": mem0.__version__,
      "python_version": sys.version, "os": sys.platform,
      "os_version": platform.version(), "os_release": platform.release(),
      "processor": platform.processor(), "machine": platform.machine(),
      **properties,
    }

各事件附带的 properties（mem0/memory/main.py）：mem0.init / mem0.add / mem0.search / mem0.get_all / mem0.update / mem0.delete / mem0.reset / mem0.notice_displayed 等事件名，加上：

    {"version": ..., "keys": [...], "encoded_ids": {...}, "sync_type": "sync"}
    {"limit": ..., "threshold": ..., "explain": ..., "advanced_filters": bool}
    {"memory_id": "<uuid>"}          ← get/update/delete/history

其中 keys 是过滤字段的名字列表，encoded_ids 是 md5（mem0/memory/utils.py 的 process_telemetry_filters）：

    encoded_ids["user_id"] = hashlib.md5(filters["user_id"].encode()).hexdigest()

另外 capture_event 还会带 memory_instance.collection_name（本项目是 her_memory）、向量维度 1024、以及向量库/LLM/嵌入类的模块名。

结论：不含记忆正文，也不含明文联系人 id；但外发了「这台机器 + 这套模型/库 + 每次操作的类型与时间 + 记忆条数与集合名（her_memory）」。对私人陪伴项目来说这仍属于不该外发的一类信息（可按条数、频率、活跃时段侧写使用强度）。

## ② 方案

### 2.1 把遥测彻底关掉（三层，缺一不可）

第一层，启动环境（当前已有，需让新进程真正带上）：index.js 的 _spawnMemoryEngine env 注入六个变量，启动记忆引擎.bat 同：

    MEM0_TELEMETRY=False  ANONYMIZED_TELEMETRY=False  CHROMA_TELEMETRY=False
    DO_NOT_TRACK=1  HF_HUB_DISABLE_TELEMETRY=1  SCARF_NO_ANALYTICS=true

按 1.11 的核查，这六个里只有 MEM0_TELEMETRY 有读点（另五个对应的库本机都没装，属于零成本保险），但它一个就足以关干净：运行期守卫验证里，设了开关后 add/search/get_all 照常、非 loopback 的外发尝试为零。

第二层，sidecar 自保（新增，与启动方式无关）：python/memory_service.py 顶部、任何 import mem0 之前设好变量。因为 mem0 的开关是 import 时读一次，这一层保证「谁拉起都关」（同时把这六个变量的默认值固化在代码里，不依赖启动器是否记得写）。

    # memory_service.py 顶部（第 14 行附近，import 段之后、任何 mem0 导入之前）
    os.environ.setdefault('MEM0_TELEMETRY', 'False')
    os.environ.setdefault('ANONYMIZED_TELEMETRY', 'False')
    os.environ.setdefault('DO_NOT_TRACK', '1')

第三层，导入后硬关 + 自检告警（新增，防将来变量改名/被覆盖）：在 build_memory 的 `from mem0 import Memory` 之后加一个 _force_telemetry_off()，并写一行明确的日志，把「隐私开关失效」变成可见事件而不是静默回归：

    def _force_telemetry_off():
        from mem0.memory import telemetry as t
        if t.MEM0_TELEMETRY:
            sys.stdout.write('[mem] 警告：遥测开关没生效，已强制关闭（MEM0_TELEMETRY=%r）\n'
                             % os.environ.get('MEM0_TELEMETRY'))
        t.MEM0_TELEMETRY = False
        try: t._shutdown_oss_telemetry()
        except Exception: pass
        try: t.client_telemetry.close()
        except Exception: pass

顺带处置第 138 行的 telemetry: False：保留可以（无害，表达意图），但注释要改成实话——它在 mem0 2.0.20 里是空操作，真正生效的是环境变量。或者直接删掉，避免误以为配置层已经关掉。

网络层兜底（可选，不写代码）：hosts 里把 us.i.posthog.com 与 raw.githubusercontent.com 指到 127.0.0.1。注意不要用「禁止 python.exe 全部出网」这类规则——mem0 的提炼模型是 python 侧发起的 HTTPS，一刀切会把记忆提炼打死。

### 2.2 让写入失败可见（五个动作，都不改行为语义）

1. sidecar 记原因：统一 except 里加一行 stdout（进 mem-engine.log），把路径与错误文本写出来：

       sys.stdout.write('[mem] %s 失败: %s\n' % (path, str(e)[:300])); sys.stdout.flush()

2. sidecar 区分 400/500：空 text / 空 query / 非 UTF-8 请求体一律返回 400 且带中文原因（这是调用方的错，不该报 500，更不该静默）。同时 _body() 解析失败时直接回 400 并返回 None，让 do_POST 早退，不再把 {} 当成正常请求。

3. soul.addMemory 返回真实状态：返回值加 engine 与 ok 字段（{ ok, engine: 'mem0' | 'local-fallback', id, error }），失败时除了本地 JSON 再记一个 pendingEngine 标记（写进新的 memory-fallback.json，或在 memory-meta.json 里加 pending:true），供后台显示与补迁。

4. 后台可见（禁黑盒）：
   - GET panel/memory 返回值加 health: { engine, writeFails, lastFailAt, lastFailReason, pendingLocal }；
   - 记忆页顶部：引擎写入失败过就显示红字（含最后一条原因与次数），并显示「只在本地、未进引擎：N 条」+「补迁这 N 条」按钮；
   - 实况直播（activity 队列，index.js 第 736 行）加一条 '[记忆] 写入失败，已暂存本地（第 N 次）：<原因>'；
   - 检索降级也进实况（现在只有一行 60 秒节流的 log）：'[记忆] 本轮检索降级到本地（原因）'。

5. 补迁不再依赖一次性 flag：_autoMigrateLegacyMemory 的短路保留（它管的是旧格式迁移），但新增一个与它独立的「本地暂存补迁」逻辑：任何时刻只要 pendingLocal > 0，后台按钮可点，或每 N 小时自动重试一次，成功后清 pending。

### 2.3 空 query 不再打引擎（三处护栏）

1. _retrieveHybrid 入口护栏：query 去空白后为空 → 直接走本地检索，不发引擎请求（这类请求 100% 失败，只会制造 500 与降级日志）：

       const q = String(query || '').trim();
       if (!q) return this._retrieveHybridLocal(query, peerKey);

2. proactive 换一个真实可用的检索词：不得不用空串时，退化为最近的入站文本，再退化为世界引擎的 statusLine，最后退化为「最近」：

       const seed = extra.seed || (extra.flowItem && extra.flowItem.text) || (world && world.statusLine) || '';
       const memories = await this._retrieveHybrid(seed, peerKey);

3. reply 的入站空文本护栏：text 为空但 mediaCount > 0 时用「（他发来一张图/一条语音）」这类中性文本做检索词（同时也是给模型的输入），避免空 query 与空输入同时出现。

### 2.4 编码层：谁把 GBK 变成了 U+FFFD 与空 query

事实链（两层）：

    Node 层：http 的 req.on('data') 给的是 Buffer，`data += c` 触发 utf8 解码（替换非法字节为 U+FFFD）。
             非法序列不会抛错，只会变成替换字符，于是 U+FFFD 被原样写进记忆（1.10 那条）。
    Python 层：_body() 对同一段字节做严格 utf-8 解码 → UnicodeDecodeError → 被 except 吞成 {} →
             字段全空 → mem0 校验报 Invalid query/空文本 → 500 → 插件静默降级。

修法（两侧各一层，另加一条调用习惯）：

    Node 侧（index.js readBody 与 panel/memory 路由）：解析后检查 `/\uFFFD/`，命中即 400：
      return send(400, { ok: false, error: '提交内容不是合法 UTF-8（常见于从 GBK 控制台/终端粘贴中文）。请把内容存成 UTF-8 文件后用 --data-binary @文件 提交。' });
    Node 侧（soul.addMemory 入口）：同样拒绝含 U+FFFD 的 text，防止世界引擎/自评/自述等自动路径把坏字符串写进库里。
    Python 侧（_body）：UnicodeDecodeError 与 JSON 错误分别回 400 与明确原因（见 2.2 第 2 条）。
    调用习惯：手工验证接口时，中文请求体一律写成文件再 --data-binary @文件（本调查已实测过：直接在内置终端里带中文发请求会被判成空 query）。

### 2.5 明确不做的事

- 不删也不改 mem0 的存储文件（docstore / faiss / embed-dims），本次改动不碰向量。
- 不引入新的外发依赖，不换向量库，不动提炼模型链路。
- 不自动删除那条已损坏的记忆（删记忆是用户决定），只做标记与提示。

| R4 | Node 侧 U+FFFD 校验误伤 | 用户合法输入里含替换字符（几乎不可能，只有编码事故才产生） | 该次提交被拒并提示 | 提示里给正确提交方式；校验只拒绝替换字符，不拒绝 emoji/其他语言 | 去掉那一行判断 |

| R6 | pending 标记写盘过于频繁 | 引擎长时间不可用 | 磁盘抖动 | 同原因 60 秒节流 + 落盘用原子写 | 关掉 pending 落盘，仅内存计数 |

### 6.1b 遥测开关（运行期守卫验证：证明「关掉之后真的没有外发尝试」）

    real_connect = socket.socket.connect
    def guard_connect(self, addr):
        host = addr[0] if isinstance(addr, tuple) and addr else str(addr)
        if isinstance(host, str) and host not in ('127.0.0.1', '::1', 'localhost'):
            BLOCKED.append(('connect', host)); raise OSError('blocked-by-guard')
        return real_connect(self, addr)
    socket.socket.connect = guard_connect
    # getaddrinfo 同样加守卫；os.environ['MEM0_DIR'] 指向临时目录；store_path 指向临时目录

### 6.7 结论口径

- 遥测来源＝mem0 2.0.20 自身的两个 PostHog 客户端，配置层关不掉，唯一开关是环境变量，且当前在跑的引擎尚未带上（需重启才生效）。
