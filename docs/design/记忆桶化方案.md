# 记忆桶化 + 遗忘曲线 施工方案

> **状态：已实施**（2026-09-13 全部落地）。三个桶 + 遗忘曲线（只降权永不删）+ 幂等迁移（判桶、补回引擎 id、损坏条目进人工清单）+ 后台界面与五处写入路径。实现细节见《工程实施档案（减法轮 + 加法轮 E1–E4）》与 `docs/记忆系统设计.md` 第三节。

施工目标目录：wechat-companion/。本文件只描述怎么改，不含任何实际改动。

引用约定：记忆相关的函数（catOf / catLabel / memoriesView / addMemory / editMemory / pinMemory / _retrieveHybridLocal / _retrieveHybrid / migrateLegacyMemory / _jsonAdd / _metaSet / _systemPrompt 的记忆注入段 / recordConversation）在冻结快照 research/snapshot-已部署版/src/soul.js 与 wechat-companion/src/soul.js 中逐字一致（逐函数比对结论：全部相同），所以行号以快照为准即可。world-engine.js 与 index.js 当前比快照多出话量档位（talkDelta）与心情派生（moodNow）两处改动，这两个文件的定位一律给函数名 + 代码片段，行号仅供快速跳转。

一句话方案：记忆的 7 个元数据砍成 3 个桶（会淡忘 / 固化 / 她自己的感受）+ 时间，桶只存一处（memory-meta.json 升级为 v2），检索打分从「重要度 + 置顶 + 越新越高」换成「桶权重 × 相关性」，长期不提的条目权重按指数曲线降到 0.25 为下限但永不删除；现有 6 条按规则迁移并顺手修好本地镜像与 mem0 之间的 id 断链。

## ① 现状与证据

### 1.1 一条记忆现在带 7 个元数据，外加两个隐藏字段

本地 JSON 条目的全部字段（src/soul.js 的 _jsonAdd，快照 555 行到 575 行）：

    const e = {
      id: rid(), who: item.who || '', text,
      importance: item.importance || 3, tags: item.tags || [],
      todo: item.todo || null, pinned: !!item.pinned, ts: Date.now(), hits: 0,
    };
    if (item.mid) e.mid = item.mid;

mem0 侧真正落盘的单条结构（只读实测：~/.dsh/wechat-companion/mem0-store/her_memory.json 的 docstore 项）：

    {"importance":5,"tags":[],"pinned":false,"ts":1789250424903,"source":"migrated",
     "user_id":"global","role":"user","data":"我叫锦鲤","hash":"...",
     "created_at":"2026-09-13T10:06:17.813509+00:00","updated_at":"...","text_lemmatized":"我叫锦鲤"}

第三个文件 memory-meta.json 单独存 mem0 条目的重要度与置顶覆盖（src/soul.js 的 _metaFile / _metaSet，快照 369 行到 378 行；只读实测当前内容为 {}）。

结论：同一条记忆的「重要度 / 置顶」可以同时出现在 mem0 metadata、本地 memory.json 兜底镜像、memory-meta.json 覆盖层三处；这正是本项目已知的「同一状态多处写入」病症（docs/项目状态.md 第 121 行那条纪律：生成标签与筛选必须同源）。

### 1.3 归属三类「我 / 她 / 世界」在两个消费者那里推导结果不一致

归属的唯一定义在 catOf（快照 627 行到 635 行）：

    catOf(e = {}) {
      const md = e.metadata || {};
      const c = md.cat || e.cat;
      if (c === 'you' || c === 'her' || c === 'world') return c;
      const src = String(md.source || e.source || '');
      if (src === 'self' || e.who === 'self') return 'her';
      if (src === 'life') return 'world';
      return 'you';
    }

提示词的记忆注入段却是另一套判定（_systemPrompt，快照 994 行到 995 行）：

    const isSelfMem = (m) => m && (m.who === 'self' || m.source === 'self');
    const memLines = (info.memories || []).filter((m) => !isSelfMem(m)).map(...);
    const ownLines = (info.memories || []).filter(isSelfMem).map(...);

世界引擎写生活流水时用的是 who:'self' + source:'life'（world-engine.js 「生活流水入她的记忆」段）：

    await this.soul.addMemory({ who: 'self', text: '（生活）' + f.text, importance: 2, tags: ['生活'], source: 'life' });

同一条流水：catOf 判成 world（后台显示「世界」），isSelfMem 判成她自己的话（提示词里进「你自己说过的话，务必与之一致」那一行）。全仓没有一处同时具备这两套判定的一致性检查。

### 1.4 现在的「想起」没有遗忘，只有「新的加分」，而且引擎给的相似度被丢掉

本地兜底打分（_retrieveHybridLocal，快照 770 行到 780 行）：

    const hay = (e.tags || []).concat([e.text]).join(' ');
    const kw = Math.min(6, this._zhGrams(q, 20).filter(function (g) { return hay.indexOf(g) >= 0; }).length);
    const cos = cosMap ? (cosMap.get(e.id) || 0) : 0;
    const recency = Math.exp(-daysAgo(e.ts) / 30);
    const score = (e.importance || 3) * 2 + kw * 3 + cos * 4 + recency * 2 + (e.pinned ? 100 : 0);

mem0 主力路径（_retrieveHybrid，快照 785 行到 826 行）把三路检索结果拼起来后只做一件事：

    out.push({ id: e.id, text: ..., ts: ..., importance: ..., tags: ..., pinned: ..., who: ..., source: ... });
    out.sort((a, b) => (b.pinned ? 100 : 0) - (a.pinned ? 100 : 0));

mem0 返回的 score（实测 /search 返回里带 score，例如 0.546）没有被放进 out，也没有参与排序。

全仓检索 decay / 遗忘 只命中 deform.js 的压力衰减（与记忆无关）。结论：记忆层目前是「只增不减」，A15 的遗忘曲线零落地；ts 只在本地路径参与打分，方向是「越新越高」，不是「长期不提就降」。

### 1.6 本地镜像与 mem0 之间的 mid 链是断的

6 条本地条目里没有任何一条带 mid（只读实测，逐条 mid=None）。mid 只在 addMemory 新写入时才会写：

    this._jsonAdd({ who: ..., text, importance: ..., tags: ..., todo: ..., pinned: ..., mid: id });

而迁移路径 migrateLegacyMemory 的回调只把数据发给引擎，没有把返回的 id 回填到本地条目（快照 731 行到 741 行，返回 { added, total }）。

后果一：「让她忘掉」在引擎在线时走 deleteMemory → mem0 删除 → _jsonDeleteByMid(memId)，按 mid 在本地找条目，找不到，于是本地镜像留着这条；引擎一挂，兜底路径会把它重新想起来，删除等于没删。

    async deleteMemory(memId) { ... await this.memory.remove(memId); this._metaSet(memId, null); this._jsonDeleteByMid(memId); ... }

后果二：改正文同理，本地镜像会一直停留在旧文本（_jsonEditByMid 的 find(e => e.mid === mid) 永远返回 undefined）。

结论：桶化迁移必须顺手把 mid 按 (who, 正文) 配对回填，否则新写的桶键同样会挂在错误的 id 上。

## ② 方案

### 2.1 两个正交轴：归属保留，新增桶

「我 / 她 / 世界」回答的是「这条记忆是谁的事」，桶回答的是「它会不会淡忘、它以什么权重被想起」。两者不合并。

| 轴 | 取值 | 谁决定 | 谁消费 |
|---|---|---|---|
| 归属 cat | 我 / 她 / 世界 | 写入时算一次（原 source 信息并进来） | 后台芯片与筛选、提示词的两行分组 |
| 桶 bucket | 会淡忘 / 固化 / 她自己的感受 | 写入时定一次，之后只由人改 | 检索权重、后台列表 |

举个同时用上两个轴的例子：世界生活流水 = 世界 × 会淡忘；她聊天里的自述（我下周去杭州）= 她 × 她自己的感受；后台手写的一条事实 = 我 × 固化。

不合并的理由（取舍写清楚）：如果做成一个五值枚举（我-会淡忘 / 我-固化 / 她-感受 / 世界-会淡忘 / 世界-固化），提示词分组与寿命就耦合在一起，改任意一边都要动另一边；而且「归属三选一」是已经验收过的交互（test/console-smoke.mjs 的芯片断言、test/fix-smoke.mjs 的 catLabel 断言都盯着它），合并等于把已验收的界面推倒重做。

### 2.2 三个桶的定义与默认判定

    dynamic    会淡忘      聊天里提炼出来的事、世界引擎的生活流水
    permanent  固化        后台手写的事实、女娲导入的记忆种子、人手动固化的任何一条
    feel       她自己的感受 她的自述（立场/打算/喜好/约定）、世界引擎的成长理由

写入时的默认判定（纯函数，不调模型、不额外花钱）：

    function defaultBucket({ cat = '', source = '', text = '' } = {}) {
      if (source === 'manual' || source === 'handcraft') return 'permanent';
      if (/^（成长）/.test(String(text))) return 'feel';
      if (cat === 'her') return 'feel';
      return 'dynamic';
    }

桶一旦写入不再自动变化（除人手动改）。这条是为了不重演「心情存三处、每个消费者算法不同」的老问题：桶只有一个写入口，只有读。

### 2.3 importance / pinned / tags / todo / hits / source 的取舍（必答问题 3）

| 旧字段 | 处置 | 替代物 | 说明 |
|---|---|---|---|
| importance | 删掉存储字段 | 桶权重 | 抽取提示词仍然让模型给 1 到 5 分，但只在入库前用一次做闸门（沿用 soul.js 1283 行的 `(it.importance \|\| 3) < 2` 过滤），落库时丢弃；后台不再有滑杆，不参与打分 |
| pinned | 删掉布尔字段 | permanent 桶 | 后台的「钉住」按钮改成「固化」。行为有一处刻意的变化：旧 pinned 是 +100 分（永远占据 topK 名额），新 permanent 只是不衰减 + 正常相关性打分；若候选不足 topK，permanent 条目补位。理由：置顶的老行为会把身份类条目塞进所有不相关的对话，是「她老提同一件事」的一个来源 |
| tags | 删掉 | cat + bucket | 现在写入的标签值（生活 / 成长 / 自述 / 称呼 / 饮食）表达的全是归属或来源，已被 cat + bucket 覆盖；搜索改成只搜正文 |
| todo | 删掉 | 无（A8 承诺闭环另起队列） | 零读取点的死字段；承诺不寄生在记忆条目里 |
| hits | 删掉 | lastHit（时间戳） | 遗忘曲线的锚点，且是真正会被读的字段 |
| source | 删掉 | cat | 写入时把 source 折算成 cat，之后只认 cat；提示词分组也改成读 cat |

砍完剩下：id、who（检索分区键）、text、cat、ts，加上桶文件里的 bucket 与 lastHit。从 7 个元数据降到 2 个（cat、bucket）+ 时间。

### 2.4 遗忘曲线（必答问题 4）

权重公式（permanent 恒为 1，不参与衰减）：

    age  = (now - lastHit) / 86400000            天，lastHit 初始值取该条记忆的 ts，不是入库时间
    FLOOR = 0.25
    TAU   = { dynamic: 21, feel: 60 }            天
    w = permanent ? 1 : FLOOR + (1 - FLOOR) * Math.exp(-age / TAU)

几个点位的取值（用于验收时对照）：

| 距上次被提起 | dynamic 的 w | feel 的 w |
|---|---|---|
| 0 天 | 1.00 | 1.00 |
| 7 天 | 0.69 | 0.85 |
| 21 天 | 0.43 | 0.71 |
| 60 天 | 0.28 | 0.47 |
| 180 天 | 0.25 | 0.31 |
| 任意久 | 0.25 | 0.25 |

回升：条目被真正注入提示词（本轮进了 topK 并随回复发出）才把 lastHit 置为当前时间，w 回到 1；同一 id 6 小时内只写一次盘（节流），避免每轮回复都改文件。被检索命中但没进 topK 的不算。

检索打分：

    本地兜底路径：score = w * (2 + kw * 3 + cos * 4)
      （替换原来的 importance*2 + recency*2 + pinned*100）

    mem0 主力路径：把引擎返回的 score 补进候选，排序键用 w * (0.4 + score)
      （引擎的语义相似度本来就在返回里，现在被丢掉；补上它就不再只按置顶排）

不删的保证：衰减只改权重，不改 text、不删条目、不删向量、不动 mem0；后台默认列出全部条目（含 w=0.25 的），并给「很久没提过」标记；一条 180 天没被提起的流水仍然能被关键词/语义命中并出现在列表里，只是排名靠后。

### 2.5 存储与引擎边界：改哪边、要不要迁向量库（必答问题 5）

只改 Node 侧。python/memory_service.py 零改动；不重建向量库（桶与权重都不进向量，faiss 与 docstore 的 id、向量维度 1024 全部不动），所以不存在维度护栏报错与重建风险。

桶的唯一存放处：memory-meta.json 升级为 v2。

    {
      "v": 2,
      "<mem0 id 或本地条目 id>": { "bucket": "dynamic", "lastHit": 1789254227872 },
      ...
    }

为什么必须放在 Node 侧的这个文件里（有代码依据）：mem0 sidecar 的 /update 只能改正文，没有任何改 metadata 的入口：

    if path == '/update':
        data = b.get('data') or {}
        with _lock:
            m.update(memory_id=str(b.get('id') or ''), data=str(data.get('text') or ''))
        return self._send(200, {'ok': True})

而 mem0 的 docstore 文件被进程持有在内存里，从外部直接改文件会被内存副本覆盖。所以「人手动把一条改成固化」这件事只能落在 Node 侧。沿用既有的 memory-meta.json（而不是新起一个 memory-buckets.json）是为了不多出第四个文件，并且让 panel/reset 的清理清单（index.js 里 want.memory 分支的 targets）与备份清单不用改。

mem0 metadata 的新写法：addMemory 只写 { cat, ts }，桶不写进 mem0（避免两处都有）。旧条目里遗留的 importance / tags / pinned 字段保留原样不清（不动引擎存储文件），但后台视图不再返回它们。

检索分区不变：仍按 who 三路（peerKey / global / self）。

### 2.6 提示词注入的改法（行数不增）

保持今天的两行，只换判定字段与措辞：

    const memLines = (info.memories || []).filter((m) => m.cat === 'you').map(...)          // 【你记得的关于对方/最近的事】

### 4.2 迁移算法（migrateBuckets，幂等，只写一个文件）

1. 备份留痕：把 memory-meta.json 原样复制成 memory-meta.v1.json（旧格式 {id:{importance,pinned}} 的内容不丢），随后重建为 v2 结构。当前实测该文件是 {}，这一步是空转换，但非空情形必须覆盖。
2. 读本地镜像：getMemories().entries。
3. 读引擎全量：memClient.list()，得到 [{ id, text, who, metadata }]。引擎未就绪时跳过第 4 步并把第 5 步标记为 pending（幂等重跑补上）。
4. 配对并回填 mid：对每条本地条目，用（归一化 who，正文）精确匹配 mem0 条目；归一化规则是本地 who 为空一律当作 'global'（实测「我叫锦鲤」本地 who=''、mem0 user_id='global'），空白字符两端裁剪后比较。匹配成功则把 mid 写回 memory.json（修 1.6 的断链），并把桶键写成 mem0 id。配对键必须带 who，避免同名文本跨联系人串键。
5. 判桶并写 memory-meta.json：
   - 手写入口与女娲种子（判据：本地条目的 cat 为空且有 who、或模型来源为 manual）：permanent
   - who='self' 且正文以 （生活） 开头：cat=world，bucket=dynamic
   - who='self' 且正文以 （成长） 开头：cat=her，bucket=feel
   - who='self' 其余自述：cat=her，bucket=feel
   - 其余（关于他的事）：cat=you，bucket=dynamic
   - 已有 v2 记录的条目保持不动
6. 损坏检测：正文或标签里出现 U+FFFD 替换字符，或匹配不上任何 mem0 条目且正文长度小于 4：不进桶，写进 memory-meta-review.json（{id, text, reason}），迁移返回 review 计数；后台记忆页顶部给出提示。这类条目不自动删除（不替用户做删记忆的决定）。
7. 原子写：memory-meta.json 走既有的 writeJson（先写临时文件再 rename），任何一步抛错则不置 memoryBucketsMigrated 标志，下轮重试；已经写坏的情形用 4.1 的备份覆盖。

幂等性：重复跑的结果一致（第 5 步有「已有记录不动」、第 4 步的 mid 回填是覆盖写入）；测试用例要求连跑两次输出相同（见 ⑥ 第 2 组）。
